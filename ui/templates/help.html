What is MPAC?

The problem: platforms, vendors, and AI labs all make claims about how well their AI performs at a given task. The numbers that exist are often produced by the same party being evaluated. When it comes to compliance with regulatory frameworks like the Digital Services Act, you can't afford to blindly trust the claims of these platforms as they apply to your use of AI in critical business workflows.

The solution: MPAC (Multi-Provider Agent Consensus) is a testing harness for AI classification. It runs evaluations across any combination of models and providers, giving every model identical inputs and producing structured, time-stamped outputs with their responses, reasoning, and core metrics. MPAC provides that data at any point in time, on-demand. It's easy for companies to claim competancy, MPAC makes them prove it.

hub

Bring your own models

MPAC has support for multiple different inference providers; you can add multiple backends by copying your API keys from Anthropic, Google, DeepSeek, and more. You can also bring your own local, custom, or open source models through vLLM, ollama, llama.cpp, and other OpenAI API-compatible backends (reach out to info@pelidum.com to discuss on-prem deployment options).

fact_check

Bring your own ground truth

MPAC's core philosophy is rooted in ground truth produced by human experts. It never relies on LLM-as-judge, and instead uses simple consensus or applies inter-rater reliability principles when a correct answer is not known (multiple answers from multiple models are weighted against historical F1 task performance to produce a single high-quality consensus).

tune

Bring your own quality bar

MPAC eschews the current "highest number wins" philosophy in LLM evaluations, and focuses on several core metrics instead for a fuller picture of performance (Precision, Recall, F1, TTFT, TPS, Latency p50/p95, Cost). These are complex, non-deterministic systems that cannot and should not be boiled down to any single number.

Core Concepts

assignment

Test

A named collection of items and a methodology. Evaluation tests score each model response against a known correct answer (precision/recall/F1). Survey tests collect open-ended model responses when a correct answer is not known and score them using consensus and inter-rater reliability methods.

quiz

Test Item

A single prompt within a test: a piece of content to classify, a question to answer, or a scenario to evaluate. Items can include text, images, audio, and video. Evaluation items carry a canonical answer from a human expert or multi-rater process.

play_circle

Test Run

An execution of a test across one or more models. Every model gets the same prompt under the same conditions. Each run records every answer alongside precision, recall, F1, refusal rate, time to first token (TTFT), output tokens/sec (TPS), end-to-end latency (p50/p95), token usage, and cost per model.

memory

Model

A specific LLM identified by provider and model ID. MPAC supports commercial APIs (OpenAI, Anthropic, Mistral), open-source models (Llama, Qwen, DeepSeek), and private or on-prem deployments via vLLM, ollama, and llama.cpp. See Models for the full catalog.

cloud

Backend

An inference endpoint that routes requests to models: OpenAI, Anthropic, OpenRouter, vLLM, Ollama, Llama.cpp, and more are all available options. Admins register backends; MPAC handles routing, concurrency, and rate limiting automatically. Mix and match local and remote models in the same run!

area_chart

Metrics

MPAC reports both classic ML metrics and modern LLM performance stats:

Precision: Of all positive predictions, how many were correct?
Recall: Of all actual positives, how many were found?
F1: Harmonic mean of precision and recall.
TTFT: Time to first token: request dispatch to the first streamed token, in seconds.
TPS: Output tokens per second after the first token (excludes prefill).
Latency: End-to-end request time, dispatch to last token, in seconds.

The Metrics page aggregates these across runs for cross-model comparison.

User Journeys

play_arrow

Run an evaluation

The fastest path to results. Use a pre-built test from the library against any set of models. Note: requires you to register a backend first.

  1. 1.Go to Tests and browse the library. Tests are grouped by provider/source (e.g. Gab Hate Corpus, MMLU, internal datasets).
  2. 2.Open a test to review its items, harm area, and methodology before committing to a run.
  3. 3.Click Run Test. Select one or more models; you can mix providers freely (e.g. GPT-4o alongside Llama-3 and Qwen3.5).
  4. 4.Set a sample size if you want a subset of the dataset. Useful for quick sanity checks before a full run; defaults to 500 max for large datasets unless overridden.
  5. 5.Launch. All models receive the same items, and results stream back in real-time.
  6. 6.Once complete, inspect the run results for per-model precision/recall/F1/refusal rate, individual answer review, and cost/latency breakdown.

poll

Run a survey

When you don't know the answer in advance, but want to get an informed consensus from multiple models for a given task (e.g. high-stakes classification), surveys are the way to go.

  1. 1.Go to Tests and find a survey, or create one under New Test → Survey.
  2. 2.Open the survey to review its items and methodology.
  3. 3.Click Run Survey. Select two or more models; consensus improves with model diversity.
  4. 4.Set a sample size if you want a subset of the items.
  5. 5.Launch. Each model answers every item independently; results stream back in real-time.
  6. 6.Once complete, inspect the consensus results. Answers from multiple models are weighted against historical F1 task performance to produce a high-quality consensus for each item.

Tip: Surveys can also be used for more abstract questions; see the "Trust and Safety Core Harm Area Survey" for a task that asks models what harm verticals they're comfortable working on according to their training instructions / content guardrails.

Build a test

Bring your own golden set: expert-vetted items specific to your platform, harm area, or use case.

  1. 1.Go to Tests → New Test. Choose Evaluation (scored against a canonical answer) or Survey (open-ended, informed consensus response).
  2. 2.Set the name, source/provider, and visibility: private (owner only), org-wide, or public.
  3. 3.Add items directly in the table: type one at a time, paste from Google Sheets / Excel, or use Import Files to create items from attachments. For very large datasets, consider using the API.
  4. 4.Evaluation items require a canonical_answer; this is your ground truth, ideally from expert review with multi-rater agreement.
  5. 5.Attach files where relevant; MPAC supports text, image, audio, and video modalities within the same test (see the Debug Animals Evaluation for an example of mixed modalities). Drag files directly onto table rows, or use Import Files to create items with attachments in one step.

Evaluation item JSON format:

            {
              "test_id": "<test-id>",
              "question": "Does this content constitute hate speech?",
              "choices": ["Yes", "No"],
              "canonical_answer": "Yes",
              "context": "Optional: source text or content shown to the model."
            }

Use the API / CLI

MPAC exposes a high-performance gRPC API. Your API key is in Settings. All calls require an x-api-key metadata header.

Discover all service methods

grpcurl {your-instance}-api.mpac.pelidum.com:443 list pelidum.services.grpc.mpac.MPAC

Uses gRPC server reflection.

grpcurl -H "x-api-key: YOUR_API_KEY" \
  -d '{"limit": 25}' \
  {your-instance}-api.mpac.pelidum.com:443 pelidum.services.grpc.mpac.MPAC/ListTests

# Get a specific test
grpcurl -H "x-api-key: YOUR_API_KEY" \
  -d '{"id": "TEST_ID"}' \

Client Integration

Uses server reflection; no .proto files needed.

Install: pip install grpcio grpcio-reflection protobuf 

import grpc
from grpc_reflection.v1alpha.proto_reflection_descriptor_database import (
    ProtoReflectionDescriptorDatabase,
)
from google.protobuf.descriptor_pool import DescriptorPool
from google.protobuf.message_factory import GetMessageClass

HOST    = "{your-instance}-api.mpac.pelidum.com:443"
API_KEY = "YOUR_API_KEY"

channel = grpc.secure_channel(HOST, grpc.ssl_channel_credentials())

# Pull full schema from the server; no local .proto files required
db   = ProtoReflectionDescriptorDatabase(channel)
pool = DescriptorPool(db)
svc  = pool.FindServiceByName("pelidum.services.grpc.mpac.MPAC")

# Print all available methods
methods = sorted(m.name for m in svc.methods)
[print(m) for m in methods]

# List tests
ListRequest = GetMessageClass(
    pool.FindMessageTypeByName("pelidum.services.grpc.mpac.ListRequest")
)
Test = GetMessageClass(
    pool.FindMessageTypeByName("pelidum.services.grpc.mpac.Test")
)

list_tests = channel.unary_stream(
    "/pelidum.services.grpc.mpac.MPAC/ListTests",
    request_serializer=lambda r: r.SerializeToString(),
    response_deserializer=Test.FromString,
)

results = {}
for test in list_tests(ListRequest(limit=25), metadata=[("x-api-key", API_KEY)]):
    results[test.name] = test.item_count

for name, count in sorted(results.items()):
    print(f"{name}: {count} items")

channel.close()

ListTests is server-streaming; the loop yields one Test per result. Swap in any method and message types to call other endpoints the same way.

Methodology

MPAC applies the same quality measurement process that human safety teams have used for decades, adapted for AI. When new human moderators ramp up, they're given tests like this until they're aligned with more experienced reviewers. MPAC runs the same process, at scale, across all models.

1

Assemble a golden set

Expert-vetted items with multi-rater agreement. Each item has a canonical correct answer established by human review, not AI judgment. MPAC's built-in library draws from sources like the Gab Hate Corpus and academic datasets; you can bring your own.

2

Zero-shot, pass@1

Each model receives the same instruction prompt and content item; no examples, no fine-tuning, no special treatment. One response per item (pass@1), matching live classifier conditions. This is the baseline; you can layer in prompting or fine-tuning later to measure improvement.

3

Multi-model execution

All selected models run against the same items under comparable conditions. Local models via vLLM; remote models via their native APIs or OpenRouter. Results are never cross-contaminated between models.

4

Standardized scoring

Model responses are extracted and compared to the canonical answer. MPAC computes precision, recall, F1, refusal rate, time to first token (TTFT), output tokens/sec (TPS), end-to-end latency (p50/p95), and cost per model, weighted by sample composition. The result is an apples-to-apples comparison across models, providers, and modalities.

Registering a Backend

At least one backend must be registered before users can run tests. Backends route inference requests to models and handle concurrency.

  1. 1.Go to Admin → Backends → New Backend.
  2. 2.Select the backend type: OpenAI, Anthropic, OpenRouter, vLLM, Ollama, or Llama.cpp.
  3. 3.Enter the base URL and API key. Set a concurrency limit; this controls how many simultaneous requests MPAC sends to this backend.
  4. 4.Enable the backend. Models served by it become available for test runs immediately.

Local backends: If you're running a local model via vLLM, Ollama, or llama.cpp, the backend URL must be reachable from the MPAC server. For cloud-hosted MPAC, this typically requires port forwarding or a tunnel (e.g. ngrok). For on-prem deployments, use the local network address directly.

Via grpcurl:

grpcurl \
  -H "x-api-key: YOUR_ADMIN_KEY" \
  -d '{
    "backend_type": "BACKEND_OPENROUTER",
    "base_url": "https://openrouter.ai/api/v1",
    "api_key": "sk-or-...",
    "enabled": true,
    "concurrency_limit": 10
  }' \
  {your-instance}-api.mpac.pelidum.com:443 \
  pelidum.services.grpc.mpac.MPAC/CreateBackend

Set per user in Admin → Users → Edit. A value of 0 means no limit.

Tokens / minute

Hard cap on token throughput. Requests exceeding this are throttled until the next minute window.

Daily spend cap

Maximum USD spend per calendar day. New runs are blocked once hit, until midnight UTC.

Monthly spend cap

Rolling 30-day spend limit for budget control across billing cycles.
